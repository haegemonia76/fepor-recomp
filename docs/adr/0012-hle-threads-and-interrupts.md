# 0012 HLE table, guest threads and interrupt delivery

Status: accepted (amends ADR 0005 and 0006)

- **HLE table**: `[[hle]]` entries in the per-version data (`crates/core/data/GFEP01.toml`, same merge rules as the analysis corrections) replace a guest function by `fepor_hle_<name>(Context*)` in the runtime. Addresses are found with `fepor-recomp find --op/--callers` and `disasm`. Only what the SDK-level structure forces is hooked: `OSSaveContext` (0x8020e550) and `OSLoadContext` (0x8020e5d0). Everything else, including the scheduler (`SelectThread`), run queues, thread APIs and the interrupt dispatcher, stays lifted guest code.
- **Threads**: every guest OSThread runs on its own host thread; only the thread holding the baton runs (`crates/runtime/src/sched.rs`). A thread switched out inside OSLoadContext parks with a token, the OSContext it will resume from. `OSLoadContext(ctx)` resumes the parked thread with that token, starts a new thread when the context has never run (at its saved SRR0), or continues the caller when it loads its own context.
- **Resume at the save point**: a thread parked after saving resumes by returning from its OSLoadContext call; the generated code then jumps to the instruction after the `bl OSSaveContext` of the same function (`resumes_at`), with registers restored from the OSContext (r3 = 1, as the SDK defines).
- **Interrupts**: external interrupts are delivered at safe points (function entry, and every backward branch through `fepor_ticks`/`fepor_poll`) when MSR[EE] is set and PI cause & mask is non-zero. Delivery emulates the vector stub prologue (the stub itself runs from RAM, which recompiled code cannot) and calls the handler found in the OS exception table. A thread switched out while inside a handler is resumed by unwinding to the delivery point with a C++ exception (`fepor::Unwind`, caught in `runtime/src/guest_shim.cpp`); this relies on C++ frames and needs an equivalent in the production backend (M7.0).
- **Devices modelled for boot**: EXI (RTC, SRAM), DI (disc reads), DSP mailbox/reset and ARAM DMA, AI sample counter, VI retrace interrupts (50 Hz PAL, 59.94 Hz otherwise), PI cause/mask, locked cache.
- **Floating-point registers across an interrupt**: the real stub saves the interrupted context's FPRs (both halves of each pair) and the OS restores them on resume. Delivery here runs the handler on the thread's own context, so a handler that switches threads left its own values in the FPRs of the interrupted thread. Symptom: random 2x8-pixel black columns in the intro video (the THP decoder's paired-single IDCT, preempted by an interrupt), 22 to 26 video frames in 440 before the fix, none in two runs after. `deliver` now puts the FPRs and FPSCR back after the resume.
