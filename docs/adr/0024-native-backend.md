# 0024 Native code backend (Cranelift)

Status: accepted (ticket M7.0, ADR 0011)

The game's code is compiled in process: `crates/jit` (`fepor-jit`) turns guest functions into native code with Cranelift, so a player needs no clang, CMake or Ninja. The generated C++ stays as the development backend (`--features cpp`, `fepor-recomp prepare --cpp`, `tools/dev-run.sh`).

- **Shape**: `Jit::install(dol, analysis, hle, ..)` holds the program; `Jit::entry(addr)` returns an `extern "C" fn(*mut Context)` like a generated function. Functions compile when first called (a table of code pointers, empty slots call `jit_resolve`): nothing is compiled at setup, about 2 ms per function and 2000 functions in a 150 s play of the first chapter. The game registers the JIT as the runtime's function resolver (`abi::set_resolver`).
- **Model**, as in the C++ backend: integer registers, CR bits (one i8 each), LR, CTR and XER live in SSA variables inside a function and are stored to the `Context` around calls and on return, reloaded after calls. A first pass collects the registers a function touches, the second emits code with the exact set to load and store. Floating-point registers always live in the context. Guest memory is `ctx.ram` (big endian, byte-swapped on load and store) with the hardware-register path for addresses outside RAM; backward branches count down `fepor_ticks` and call `fepor_poll`.
- **Floating point and paired singles** run out of line (`fp.rs`: one Rust function that executes the instruction on the context, the semantics of `ppc.h` written again in Rust, `fres`/`frsqrte` from `fp.cpp`). Correct first, not fast: an FP-heavy scene costs more than in the clang build. Inlining the common ones (`fadd`, `fmul`, `fmadds`, `ps_madd`, ...) is the next step if profiles ask for it.
- **Unwinding**: the C++ backend abandons the host frames of a thread resumed after an interrupt-time context switch with a C++ exception. Compiled code has no unwind tables: after the HLE call that resumes such a thread a compiled function sets `spr[1022]` and returns, every call site returns when it sees the flag, and `hle::run` (the Rust entry of guest calls) clears it and reports "unwound".
- **Calls**: direct calls go through the code-pointer table, `bctrl`/`blrl` through `jit_lookup`, jump tables through a `Switch`. A tail call is a call followed by a return (no `return_call`: not available for the host convention); chains of tail calls grow the host stack, which the guest thread stacks (256 MiB) absorb.
- **Polling interval**: interrupts follow wall-clock time and the guest decides when they can be delivered, at backward branches. 4096 branches between polls, right for the clang build, stalled the boot of the compiled build (two threads yielding to each other 95 000 times a second, a poll every 40 ms, the retrace and disc interrupts too late); `POLL_INTERVAL` is 256 for both backends.
- **Checked**: the 4268 instruction vectors (ADR 0008) pass through the JIT in `crates/jit/tests/vectors.rs`, sharing their loader with the C++ test (`crates/ppc-lift/tests/common`); more than 90 % of the programs change the state, so a run that did nothing cannot pass. The game boots, shows the logos, the video, the title, the menus and plays the prologue dialogues in the scripted run, and `fepor-recomp prepare` then `run` work with an empty `PATH` (no clang, cmake, ninja). `prepare` (native) is the analysis plus the copy of the game data: 1.3 s.
- **Speed**: over the same scripted 60 s (headless, so rendering and audio included) the process used 58.7 s of CPU with the JIT and 56.9 s with the C++ build generated and built in Release mode (clang -O2). Guest-only speed was not isolated.
- **Not checked**: Windows, macOS and arm64 (Cranelift and the host calling convention are used, nothing here was run on them; there is no arm64 machine to run it on, and none is needed); the battle scenes (FP and quantized loads in skinning loops are where the out-of-line floating point will show); any play past the first dialogues.
