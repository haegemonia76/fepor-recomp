# 0025 Memory patch engine and per-frame hook

Status: accepted (ticket #31; base of #32 Gecko codes, #33 TOML cheats, #34 mods, #48 memory watcher)

Cheats and mods change guest data. They all go through one layer, `fepor_runtime::patch::PatchEngine`, owned by the machine (`machine().patches`), so that they cannot silently overwrite each other and share one place where the guest is written.

- **Patch**: `Patch { addr, bytes }`. The address may be the cached (`0x80…`), uncached (`0xC0…`) or physical form; conflicts and writes use the physical address. It must lie in main RAM (24 MiB); anything else is refused when the set is registered.
- **Set**: `PatchSet { source, game_id, patches, continuous }`. `source` names the owner (`"cheat:Infinite HP"`, `"mod:foo"`), `game_id` is a `version::lookup` ID (GFEP01, GFEJ01): a set for another game than the one `set_game` was given is refused (`WrongGame`), as is any set before a game is selected. The game sets it in `main.rs` after the version check.
- **API** (all on `PatchEngine`, RAM passed as `m.ram`: `m.patches.enable(id, &mut m.ram)`):
  - `register(set) -> SetId` (disabled), `unregister(id, ram)` (reverts first);
  - `enable(id, ram)`: keeps the bytes each patch replaces and writes the patches; `disable(id, ram)` puts the kept bytes back (in reverse patch order, so overlapping patches of one set revert fully). A value the game wrote in between is lost: the bytes of the moment of enabling return. Both are no-ops when already in that state;
  - `conflicts(id)` lists the overlaps (`Conflict { with, with_source, addr, len }`) with enabled sets of **other** sources; `enable` returns `PatchError::Conflict` and writes nothing when there are any. Disabled sets never conflict; sets of one source may overlap (their owner orders them). The caller (UI, #33) decides what to show: disable the other set, or leave this one off;
  - `reapply(ram)` writes every enabled set again: after the guest's memory was replaced (save state load) or for a one-shot patch the game overwrote;
  - `frame(retraces, ram)`: the hook, see below.
- **Per-frame hook**: `intr::poll` (run from the generated or JIT code at function entries and backward branches, on the guest thread, under both backends) calls `patches.frame(hw.retraces, ram)`. When the VI retrace counter moved since the last run, it counts a frame and rewrites every enabled set with `continuous: true` (a cheat that holds a value). Several retraces between two polls are one frame. It runs between guest instructions, never concurrently with guest code, so no locking is needed. Sources that need a per-frame callback of their own (the watcher, #48) extend `frame`; do not add a second hook. The hook stays idle with no enabled set.
- **Trace**: `FEPOR_TRACE=patch` prints enable/disable and one line every 60 hooks (`patch: frame hook #N (retrace R), K enabled sets`).
- **Limit: data only.** Guest code does not run from RAM here: the functions are recompiled ahead of time (C++ backend) or when first called from the analysed DOL (JIT, ADR 0024) and the RAM copy of the instructions is never read again. A patch over instruction bytes therefore changes nothing, in either backend; code changes (Gecko code types that insert instructions, `C2`/`04` over code) cannot be expressed as patches. Code that the game loads from the disc at run time is not recompiled at all (ADR 0001). Sources must warn instead of pretending: a patch that lies in the DOL's text sections is a mistake of the source. Behaviour changes have to come from data the code reads (values, tables, text, model and resource files via mods).
- **Not covered**: persistence of enabled sets (the sources own that), thread safety (guest thread only, like `machine()`), writes through the hardware register path.
